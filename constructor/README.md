# Настройка конструктора конспектов

Конструктор работает на `constructor.html`. Редакторы создают общие черновики,
владелец проверяет их и публикует одним commit в GitHub.

## 1. Доступ к черновикам

Опубликуйте `firebase/database.rules.json` в Firebase Console → Realtime Database
→ Rules. После этого владелец может назначить пользователю роль «Редактор
конспектов» в `admin.html`. До назначения пользователь должен хотя бы один раз
войти на сайт, чтобы его email появился в каталоге аккаунтов.

Черновик сначала синхронно записывается в localStorage, затем дублируется в
IndexedDB и только после этого отправляется в `noteDrafts` Realtime Database.
При загрузке выбирается самая свежая копия. Потеря сети не блокирует работу и не
заменяет существующий текст пустым состоянием.

Подразделы хранятся внутри файла раздела в массиве `subsections`. У каждого
подраздела есть полное название, отдельная короткая подпись для меню и собственный
массив блоков. Старые блоки типа `subsection` автоматически переводятся в эту
структуру при чтении.

Определение хранит термин, разделитель (`—` или `:`) и текст отдельно. При
сборке оно превращается в ту же разметку, что используется вручную:
`<div class="definition-box"><strong>Термин</strong> — текст</div>`. Подразделы
становятся соседними элементами `<article class="topic">`, а вложенные блоки
вставляются прямо в родительский блок без служебной HTML-обёртки.

Помимо теорем, лемм и доказательств конструктор различает утверждения, следствия,
свойства, упражнения, замечания и напоминания. «Напоминание» предназначено для
ранее известного факта и оформляется как замечание, но с отдельной подписью и
иконкой часов. Формулу, доказательство или пояснение к одному утверждению следует
вкладывать в его блок, а не размещать рядом отдельными карточками.

Панель добавления блока доступна снизу редактора и по `Ctrl/⌘ + Enter`. Выбранный
блок вставляется после поля, в котором стоял курсор; кнопка во вложенной области
открывает ту же панель сразу для дочернего содержимого. На desktop ширина структуры
и предпросмотра регулируется разделителями, обе панели можно развернуть на весь
экран.

После обновления конструктора опубликуйте актуальные правила из
`firebase/database.rules.json`: в `noteDrafts` разрешено необязательное поле
`subsections`, при этом требования к роли редактора остаются прежними.

## 2. Публикация в GitHub

1. Создайте fine-grained personal access token GitHub только для репозитория
   `Almanion/Almanion.github.io`.
2. Выдайте ему единственное необходимое право: Repository permissions →
   Contents → Read and write. Задайте срок действия токена.
3. В Apps Script, где размещён `apps-script.gs`, откройте Project Settings →
   Script properties и добавьте `GITHUB_TOKEN`.
4. Необязательно добавьте `GITHUB_REPOSITORY=Almanion/Almanion.github.io` и
   `GITHUB_BRANCH=main`; такие значения уже используются по умолчанию.
5. Замените код Apps Script актуальным `apps-script.gs`, затем откройте Manage
   deployments, выберите действующий Web app, укажите New version и нажмите
   Deploy. URL менять не нужно.

Токен никогда не передаётся браузеру: он остаётся в Script properties. Backend
проверяет Firebase ID token и точный UID владельца
`2M2ZdLQcJAhluPjUVFNJ6MyQrdH2`. Все JSON-файлы и изображения попадают в один атомарный Git
commit. Если backend временно не настроен, кнопка «Скачать» сохраняет тот же
набор файлов как резервный publication bundle.

Удаление неопубликованного раздела сразу очищает его локальный и облачный черновик.
Удалять уже опубликованные разделы может только владелец: конструктор одним Git commit
обновляет манифест и удаляет файл раздела. Чтобы эта возможность появилась на сайте,
после обновления `apps-script.gs` необходимо выпустить новую версию существующего
Web app deployment; его URL при этом менять не нужно.

## 3. Сборка GitHub Pages

Workflow `.github/workflows/pages.yml` запускает `tools/build-notes.js`. Скрипт
проверяет манифесты и разделы, затем вставляет сгенерированную разметку в копии
страниц предметов внутри Pages artifact. Исходная ручная HTML-разметка не
перезаписывается.

## 4. История, проверка и изображения

Конструктор сохраняет до 50 локальных страховочных версий раздела в IndexedDB и
40 последних облачных слотов в `noteDraftHistory`. Кнопки в верхней панели и
`Ctrl/⌘ + Z`, `Ctrl/⌘ + Shift + Z` (`Ctrl + Y` в Windows) отменяют и возвращают
изменения. В окне истории видны автор, время и краткое отличие версии; любое
состояние можно восстановить, причём вариант до восстановления остаётся в Undo.

Редакционный маршрут теперь фиксированный: `Черновик → На проверке → Опубликовано`.
Редактор отправляет материал на проверку или отзывает его. Главный администратор
может вернуть материал на доработку либо опубликовать. Комментарии к проверке
хранятся прямо в JSON раздела и не влияют на HTML, который получает читатель.

Изображение сначала синхронно остаётся на устройстве, затем конструктор пытается
загрузить его в Firebase Storage. Поэтому потеря сети не стирает выбранный файл.
Облачная метаинформация хранится в `noteDraftAssets`; главный администратор может
опубликовать изображение с другого устройства.

Для включения облачных функций:

1. Опубликуйте актуальные `firebase/database.rules.json` и
   `firebase/storage.rules`. Все правила истории, проверки и изображений уже
   объединены; `constructor/firebase-database-rules.fragment.json` оставлен как
   компактная справка по добавленной схеме.
2. Если всем редакторам нужен взаимный просмотр изображений до проверки,
   выдавайте им custom claim `contentEditor: true` через доверенный backend.
   Без claim загрузивший редактор и владелец всё равно видят файл; локальная
   копия и экспорт продолжают работать при любой ошибке Storage.
